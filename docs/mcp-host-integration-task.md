# Task: connect ZeroCreds wallet tools to Trained Assist MCP Host

## Outcome

A user or authorized agent sees the existing ZeroCreds wallet tools through `trained-assist-mcp-host`. Calling `zerocreds_wallet_form_create` with a provider and fields returns a one-time form URL, `form_id`, `connection_id` and expiry. After the person submits the form, `zerocreds_wallet_form_status` returns value-free readiness. Connection status and explicit revocation work through the same owner/profile scope. No credential value, OpenBao token, D1 service token, broad ZeroCreds admin token or static wallet API token is exposed to the model, MCP result, run artifact or log.

Keep ZeroCreds as the owner of its API, form, OpenBao and wallet metadata logic. Do not copy its domain implementation into MCP Host. MCP Host composes a pinned ZeroCreds provider, authenticates the caller and authorizes each tool. Connected Apps is a later product layer over the same `connection_id`; this task must not add another credential store or depend on the unfinished Ladder Connected Apps branch.

## Current state and boundaries

- [ZeroCreds PR #73](https://github.com/Zerocreds-com/zerocreds-server/pull/73) has the standalone stdio tools in `mcp/index.js`, the scoped Node `/api/wallet/*` routes, a sandbox D1 Worker and optional live MCP tests. Its production Node API is not deployed. The live test starts a local MCP child, local Node service and temporary OpenBao, while D1 runs in a deployed Cloudflare sandbox Worker. It does not exercise MCP Host or a real Runner/OpenCode session.
- `trained-assist-mcp-host` [composes versioned providers](https://github.com/trained-assist/trained-assist-mcp-host/blob/main/README.md#runtime), checks `allowedTools` and `authorize` on every call, and passes a trusted scope to handlers. The human Worker verifies the personal key in `MCP_IDENTITY_DB`; a run-bound machine invocation has a different Runner proof. Its `main` branch currently has no ZeroCreds provider.
- This branch adds a Worker-compatible provider descriptor at `@zerocreds/mcp/provider` (package version `0.2.0`, provider version `1.0.0`) for the four wallet tools. The stdio entry point delegates those same tools to the adapter and retains its legacy static-token path. Package `0.2.0` is not published yet.
- The wallet API accepts short-lived Ed25519 host assertions as an alternative to legacy static client tokens. ZeroCreds maps each issuer's public key ID and exact owner/profile/caller tuple to a named destination; assertion claims cannot select that destination.
- A local uncommitted `connected_apps.*` provider in the MCP Host checkout talks to Ladder's proposed Connected Apps endpoints. It is not the ZeroCreds wallet integration and must be left untouched by this task. Work in a clean worktree from the appropriate branch.

## Implementation

1. **One provider implementation, two transports.** Extract the four wallet tool schemas and handlers from ZeroCreds `mcp/index.js` into a versioned, Worker-compatible provider module in the ZeroCreds repository. Keep the existing stdio MCP entrypoint and its tool names working as a compatibility wrapper. Export a provider descriptor accepted by MCP Host (`id`, pinned `version`, `tools[]`, schemas, `requiredBindings`, handlers). Compose that descriptor in a clean MCP Host branch; do not duplicate request validation or wallet API parsing there. Reject duplicate catalog names and pin the provider version/digest as the host already requires.
2. **Trusted scope.** For the human MCP endpoint, derive an immutable wallet owner from `verifyKey()`'s `userId` and authorize the selected ServerlessAgence profile; never accept owner/profile/destination in tool arguments. For machine invocations, use the Runner-verified run/task/profile/principal binding and check that this profile belongs to the owner before enabling the tools. If a canonical mapping cannot be proven, fail closed. Keep human and machine audiences separate and grant only the four requested wallet tools in `allowedTools`.
3. **Short-lived ZeroCreds authorization.** Host assertions use Ed25519 JWTs with `aud` `zerocreds-wallet:human` or `zerocreds-wallet:machine`, wallet-safe canonical `owner_id` and `profile_id`, `caller_class`, allowed `operations`, `iat`, `exp` (at most five minutes), issuer, key ID and unique `jti`; machine calls also require `run_id`. Configure trusted public keys and exact profile mappings in `ZEROCREDS_WALLET_ASSERTION_ISSUERS_FILE` (mode 0600). Include old and new key IDs during rotation. ZeroCreds resolves the destination only from that mapping. The wallet D1 Worker consumes a SHA-256 digest of each `jti` once through `/internal/assertions/claim`; apply migration `0002_assertion_replay.sql` before enabling assertions. Retain static wallet tokens only for explicit legacy clients and local tests; never pass the Worker service token or OpenBao identity into MCP Host.
4. **API behavior.** Forward only `provider`, `kind`, schema, presentation text, TTL and idempotency key to `POST /api/wallet/forms`. Return only URL, IDs, expiry and non-secret status/version metadata. Status and connection lookup must be owner/profile-scoped; revocation is a separate explicit operation. Preserve request cancellation and timeouts, and use the idempotency key to resolve an unknown create outcome without issuing duplicate forms. Do not return raw upstream errors that can contain headers, URLs with tokens or values.
5. **Rollout.** Make the provider opt-in in sandbox first. Do not enable it on the production MCP catalog until ZeroCreds #71/#73 are safely released, the anonymous legacy-session migration is complete, persistent OpenBao is operated, and the production wallet Worker is connected. Keep existing MCP providers and ZeroCreds stdio tools unchanged during the cutover. Connected Apps can later offer discovery/list UX using the same owner-bound connection references; it must not write credential values to Ladder D1.

## Verification and acceptance

- Provider unit tests cover tool schemas, value-free responses, malformed upstream responses, cancellation/timeout, idempotent create retry and revocation. Existing ZeroCreds server, Worker and stdio MCP tests remain green.
- MCP Host tests prove that an unverified, expired, disabled or wrong-audience personal key cannot list or call ZeroCreds tools; users with different owners cannot inspect the same form or connection; an unbound run cannot call tools; the model cannot change owner, profile or destination through arguments. Other providers' catalogs and permissions remain unchanged.
- An isolated sandbox integration test runs **MCP Host → ZeroCreds Node API → OpenBao KV v2 → remote D1 Worker** using a synthetic secret. It checks pending→done→revoked, one-time submission, idempotent retry, no value in MCP/status/history/logs, and denial of another owner. A real OpenCode/Runner session must invoke the host tool before claiming agent availability.
- Document configuration ownership: MCP Host gets only its signing/transport identity and public ZeroCreds API endpoint; ZeroCreds owns assertion verification, wallet destination and Worker service token; OpenBao identities remain in the ZeroCreds/broker boundary. Publish a rollback switch that removes the new provider from the host catalog without affecting existing tools or stored connections.
