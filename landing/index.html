Mechanism How it works
step 01

Agent creates session

Your agent calls /api/session/create with a list of fields and a destination. Gets back a one-time URL. No credentials involved — just a form schema.

POST /api/session/create
fields: [{name, type, label}]
destination: "named-preset"
← { url, expires_at }
step 02

User fills the form

Agent sends the URL to the user (Telegram, email, Slack). User opens the secure form on your server, types their credentials. Data goes directly to the configured destination over HTTPS.

user → opens zerocreds.ru/f/{token}
→ fills form → POST /f/{token}
→ server writes to destination
← { ok: true }
step 03

Agent gets confirmation

Agent polls /api/session/{token}/status until "done". It learns that credentials were saved — but never sees the values. Your runtime reads them from the secret store with a separate key.

GET /session/{token}/status
← { status: "done" }

agent: continues task ✓
For Integrators

Your agent. Your secret store. One API call.

Configure named destinations once on your server. Your agent references them by name — no credentials travel in API requests.

Works with Google Secret Manager (write-only IAM role), AWS Secrets Manager, HashiCorp Vault, or plain local files. Pick what fits your stack.

Protect the session creation endpoint with ZEROCREDS_ADMIN_TOKEN. Each integration partner gets their own token.

1 ~/zerocreds-destinations.json (server config)
{
  "prod-gcp": {
    "type": "gcp_secret_manager",
    "secret": "projects/P/secrets/S",
    "credentials": "<base64 SA key>"
  }
}
↓ agent references by name
2 POST /api/session/create
{
  "title": "Connect GitHub",
  "fields": [{name, label, type}],
  "destination": "prod-gcp" ← just a name
}
↓ returns one-time URL
3 GET /api/session/{token}/status
{ status: "done" }
# credentials saved · agent never saw them
Storage Write-only destinations
GCP Secret Manager

Google Cloud

ZeroCreds uses roles/secretmanager.secretVersionAdder — it can push a new version but physically cannot read any secret back. Enforced by IAM, not code.

IAM permission: secretmanager.versions.add
NOT granted: secretmanager.versions.access
Granularity: per-secret, not project-wide
AWS Secrets Manager

Amazon Web Services

IAM policy grants only secretsmanager:PutSecretValue on a specific ARN. GetSecretValue is never in the policy — write-only by construction.

Action: secretsmanager:PutSecretValue
NOT granted: GetSecretValue
Resource: specific secret ARN
HashiCorp Vault

Self-hosted Vault

Vault policy allows create and update capabilities on the target path. read is simply omitted — Vault enforces it at the policy layer.

capabilities = ["create", "update"]
"read" not listed = denied
path: secret/data/your/path
Local File

Filesystem

Simplest option. Credentials are written as JSON to ~/agent-tokens/{uid}/{name} with mode 0600. No external dependency — works offline, ideal for single-machine setups.

path: ~/agent-tokens/{uid}/{filename}
permissions: 0600 (owner-only read)
format: JSON object of field values
